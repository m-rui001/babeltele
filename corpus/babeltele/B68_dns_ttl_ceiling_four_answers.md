### ⟦1536⟧ ⟸ raw/dnsTTL/rfc1536.txt

Cache Leaks: Every resource record returned by a server is cached for TTL seconds, where the TTL value is returned with the RR.

Full-service resolvers might not implement this caching mechanism well. They might impose a limit on the cache size or might not interpret the TTL value correctly. In either case, queries repeated within a TTL period of a RR constitute a cache leak. A GOOD/BAD IMPLEMENTATIO

### ⟦2181⟧ ⟸ raw/dnsTTL/rfc2181.txt

Consequently the use of differing TTLs in an RRSet is hereby deprecated, the TTLs of all RRs in an RRSet must be the same. Should a client receive a response containing RRs from an RRSet with differing TTLs, it should treat this as an error.

When discussing negative caching, RFC1034 section 4.3.4 refers to this technique but mentions the additional section of the response.

Time to Live (TTL) The definition of values appropriate to the TTL field in STD 13 is not as clear as it could be, with respect to how many significant bits exist, and whether the value is signed or unsigned. It is hereby specified that a TTL value is an unsigned number, with a minimum value of 0, and a maximum value of 2147483647. That is, a maximum of 2^31 - 1. ### 不可由在库文件判定(只写在这里, 不进判词与门槛)
四份 .txt 的抓取时刻与磁盘 mtime 谁新谁旧; rfc-editor.org 此刻给这四份挂的现行状态页与勘误页(97 是否已被后续草案改写这一段); 1035bis 之类在途文档把 TTL 上限改成什么; 各家 resolver 与权威服务器实际把 TTL 截到多少秒(97 明文允许“always free to place an upper bound”, 但截到多少从未由规范给出); 现网缓存里最长的一批记录实际压着多少秒; STD 13 此刻由哪几号文档构成——在库字节只能证明 97 称“TTL field in STD 13”而 87 两篇自身不带 STD: 行.
这些量要么在本机之外、要么随实现漂移, 复算通道里没有它们的位置; 门槛只认在库字节。
