### ⟦768⟧ ⟸ corpus/raw/udpCK/rfc768.txt

Postel ISI 28 August 1980 User Datagram Protocol ---------------------- Introduction ------------ This User Datagram Protocol (UDP) is defined to make available a datagram mode of packet-switched computer communication in the environment of an interconnected set of computer networks.

User Datagram Header Format Fields ------ Source Port is an optional field, when meaningful, it indicates the port of the sending process, and may be assumed to be the port to which a reply should be addressed in the absence of any other information. If not used, a value of zero is inserted. Postel [page 1] 28 Aug 1980 User Datagram Protocol RFC 768 Fields Destination Port has a meaning within the context of a particular internet destination address.

(This means the minimum value of the length is eight.) Checksum is the 16-bit one's complement of the one's complement sum of a pseudo header of information from the IP header, the UDP header, and the data, padded with zero octets at the end (if necessary) to make a multiple of two octets.

If the computed checksum is zero, it is transmitted as all ones (the equivalent in one's complement arithmetic). An all zero transmitted checksum value means that the transmitter generated no checksum (for debugging or for higher level protocols that don't care).

### ⟦1122⟧ ⟸ corpus/raw/tcpRTO/rfc1122.txt

77 4.1 USER DATAGRAM PROTOCOL -- UDP ..........................

4.1.3.4 UDP Checksums A host MUST implement the facility to generate and validate UDP checksums. An application MAY optionally be able to control whether a UDP checksum will be generated, but it MUST default to checksumming on. If a UDP datagram is received with a checksum that is non- zero and invalid, UDP MUST silently discard the datagram. An application MAY optionally be able to control whether UDP datagrams without checksums should be discarded or passed to the application.

The advisability of ever turning off UDP checksumming is very controversial. IMPLEMENTATION: There is a common implementation error in UDP checksums. Unlike the TCP checksum, the UDP checksum is optional; the value zero is transmitted in the checksum field of a UDP header to indicate the absence of a checksum. If the transmitter really calculates a UDP checksum of zero, it must transmit the checksum as all 1's (65535). No special action is required at the receiver, since zero and 65535 are equivalent in 1's complement arithmetic.

4.2.2.7 TCP Checksum: RFC-793 Section 3.1 Unlike the UDP checksum (see Section 4.1.3.4), the TCP checksum is never optional. The sender MUST generate it and the receiver MUST check it.

### ⟦8200⟧ ⟸ corpus/raw/udpCK/rfc8200.txt

Upper-Layer Checksums Any transport or other upper-layer protocol that includes the addresses from the IP header in its checksum computation must be modified for use over IPv6, to include the 128-bit IPv6 addresses instead of 32-bit IPv4 addresses.

o Unlike IPv4, the default behavior when UDP packets are originated by an IPv6 node is that the UDP checksum is not optional. That is, whenever originating a UDP packet, an IPv6 node must compute a UDP checksum over the packet and the pseudo-header, and, if that computation yields a result of zero, it must be changed to hex FFFF for placement in the UDP header. IPv6 receivers must discard UDP packets containing a zero checksum and should log the error. o As an exception to the default behavior, protocols that use UDP as a tunnel encapsulation may enable zero-checksum mode for a specific port (or set of ports) for sending and/or receiving.

### ⟦6935⟧ ⟸ corpus/raw/udpCK/rfc6935.txt

The Zero UDP Checksum Update This specification updates IPv6 to allow a zero UDP checksum in the outer encapsulating datagram of a tunnel protocol.

The following text in [RFC2460], Section 8.1, fourth bullet should be deleted: Unlike IPv4, when UDP packets are originated by an IPv6 node, the UDP checksum is not optional. That is, whenever originating a UDP packet, an IPv6 node must compute a UDP checksum over the packet and the pseudo-header, and, if that computation yields a result of zero, it must be changed to hex FFFF for placement in the UDP header. IPv6 receivers must discard UDP packets containing a zero checksum, and should log the error. This text should be replaced by: An IPv6 node associates a mode with each used UDP port (for sending and/or receiving packets).

the checksum MUST be changed to hex FFFF for placement in the UDP header, as specified in [RFC2460]. IPv6 receivers MUST by default discard UDP packets containing a zero checksum and SHOULD log the error. As an alternative, certain protocols that use UDP as a tunnel encapsulation MAY enable zero-checksum mode for a specific port (or set of ports) for sending and/or receiving.

### 本注的判断
四份文书对“一条 UDP 报文的校验和是不是非算不可、算出零值怎么办”给的不是同一个问题的四个答案, 而是把“必选与否 ⇎ 零值怎么办 ⇎ 语气的字面档 ⇎ 谁改谁”四件事拆给了四份: 768 全篇零枚大写义务词、也不用“可选”表述(optional 一词 1 枚且 0 枚与 checksum 同行, 唯一那枚贴在 Source Port), 零值只写成“发送端没算”, 算出零就发 all ones 而不给进制; 1122 把同一件事拆三层——能力 MUST implement ⇎ 每报文 MAY optionally ⇎ 默认 MUST default to checksumming on, 而“默认必须开”离同节那句 the UDP checksum is optional 只差 28 行(离“能力 MUST”差 31 行), 同一份还把 TCP 写成 never optional; 8200 说 IPv6 上“不是可选、且这是默认行为”(插入 the default behavior … is that), 全篇零大写 ⇎ 小写 must 52 枚, 是带 STD: 号的现行标准却用小写写义务; 6935 一边把那份小写原文整段引出判它该删(1 次) ⇎ 一边把同一条规则换成大写义务 4 枚并插 by default 1 枚, 再拿 MAY enable zero-checksum mode 开出口、MUST follow [RFC6936] 关出口。
于是任何“取最新/取最全”的合并都会丢东西: 按年份最新取 8200(2017), 就丢掉 6935(2013)那枚把义务降成默认的 by default 手术——而 6935 恰恰比它更新的那份早四年(年份倒序 1 处), 语气换代不按时间单向推进; 按语气最硬取 1122 的 MUST, 就丢掉 8200 把它软成小写 must、6935 又把它重新大写化这一来回。逐字搬运在此条里几乎为零(六对里五对整行为零同形, 唯一非零的 8200⇎6935 那 18 条逐字节同形全是许可样板与参考文献行, 真正差别的 1 条只差缩进), 分歧全在句子内部: 引导语、逗号(0⇎1 枚)、大小写语气档(4 枚 ⇎ 4 枚)。

四份 .txt 的抓取时刻与磁盘 mtime 谁新谁旧; rfc-editor.org 此刻给这四份挂的现行状态页与勘误页; 被 8200 废止、被 6935 更新且被 6935 引用的那份 RFC 2460 本身不在库内(本注只能读四份里对它的那处引用, 读不出它自己怎么写这条); 此后哪份在途文书又动了零校验这一段; 现网 IPv6 栈实际丢不丢零校验和的 UDP 报文(“默认丢 ⇎ 隧道旁路 ⇎ 可套接字选项覆盖”这类是实现事实, 不是文书事实); “768 早于 RFC 2119 语气表”这类年代关系只能由常识给出, 在库四份文件自身不写。
以上量要么在本机之外、要么随实现与站点漂移, 复算通道里没有它们的位置; 门槛只认在库字节。
