### ⟦2616⟧ ⟸ corpus/raw/httpRedir/rfc2616.txt

Clients with link editing capabilities ought to automatically re-link references to the Request-URI to one or more of the new references returned by the server, where possible.

If the 301 status code is received in response to a request other than GET or HEAD, the user agent MUST NOT automatically redirect the request unless it can be confirmed by the user, since this might change the conditions under which the request was issued. Note: When automatically redirecting a POST request after receiving a 301 status code, some existing HTTP/1.0 user agents will erroneously change it into a GET request.

Note: RFC 1945 and RFC 2068 specify that the client is not allowed to change the method on the redirected request. However, most existing user agent implementations treat 302 as if it were a 303 response, performing a GET on the Location field-value regardless of the original request method.

10.3.4 303 See Other The response to the request can be found under a different URI and SHOULD be retrieved using a GET method on that resource. This method exists primarily to allow the output of a POST-activated script to redirect the user agent to a selected resource.

### ⟦7231⟧ ⟸ corpus/raw/httpRedir/rfc7231.txt

If a Location header field (Section 7.1.2) is provided, the user agent MAY automatically redirect its request to the URI referenced by the Location field value, even if the specific status code is not understood.

Note: For historical reasons, a user agent MAY change the request method from POST to GET for the subsequent request.

MUST NOT change the request method if it performs an automatic redirection to that URI.

### ⟦7538⟧ ⟸ corpus/raw/httpRedir/rfc7538.txt

308 Permanent Redirect The 308 (Permanent Redirect) status code indicates that the target resource has been assigned a new permanent URI and any future references to this resource ought to use one of the enclosed URIs. Clients with link editing capabilities ought to automatically re-link references to the effective request URI (Section 5.5 of [RFC7230]) to one or more of the new references sent by the server, where possible.

A 308 response is cacheable by default; i.e., unless otherwise indicated by the method definition or explicit cache controls (see [RFC7234], Section 4.2.2). Note: This status code is similar to 301 (Moved Permanently) ([RFC7231], Section 6.4.2), except that it does not allow changing the request method from POST to GET.

Therefore, the use of status code 308 is restricted to cases where the server has sufficient confidence in the client's understanding the new code or when a fallback to the semantics of status code 300 is not problematic.

### 本注的判断
四份文书对“302 之后能不能把 POST 改成 GET”给的是四种可数的答法, 而不是四种含糊: 2616 用确认门把自动重定向挡住(“MUST NOT automatically redirect”剥引文面 3 枚, 只在 2616 存活, 判定 1), 同段又把 302 说成实现都当 303 用, 通往 GET 的正门是 303 的取回句; 7231 换成“出于历史原因 MAY change”(该措辞在 7231⇎9110 两份读得到, 判定 1), 并补一句“MUST NOT change the request method”——它排在历史原因注之后 97 行(判定 1), 即将允许读成例外; 7538 不谈改写, 只另立 308 并把义务写成散文 ought to(该份只有 2 枚大写 MUST), 30x 小节清单缩到 1 枚; 9110 收下 7231 的那句注、逐词没动(共头 19 ⇎ 共尾 19, 词序判定 1), 却把它楔进竖线引文块——不剥引文标记就一枚读不到(新增 2 枚只发生在 9110, 判定 1)——同时把改写动作列成五条编号清单(1,2,3,4,5), 清单排在注之前 78 行(判定 1)。所以“能不能改”的条文差, 在本库字节上等价于: 确认门 ⇎ 历史原因下的 MAY+例外约束 ⇎ 换一枚状态码避开含混 ⇎ 承认既成事实并给出步骤。
另一条只在本遍才显形的判断: 内容针从不因换档而丢(5 枚最宽档落空的针里, 内容针 0 枚, 全部是反向对照 4 枚+序列化对照 1 枚), 而 9110 面上 308 的枚数在四档里 0 ⇎ 2 ⇎ 17 ⇎ 13 ⇎ 0 ⇎ 2 ⇎ 17 ⇎ 13 ⇎ 0 ⇎ 2 ⇎ 12 ⇎ 13 ⇎ 0 ⇎ 2 ⇎ 17 ⇎ 13——被行界、壳行、引文竖线三种排版层折腾的从来只是可见性, 不是内容; 7538 是唯一被页眉偷走 5 枚的(0 ⇎ 0 ⇎ 5 ⇎ 0), 它整份文书就在讲这一枚码。
