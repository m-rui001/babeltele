※ 派生算术(键名即数值，表达式跑在四份原文上并逐个回算)：0⇒零值键: 表侧 11 项标记在三份表里缺席 + 网页侧 5 项在网页里缺席 + 配对层面 4 项 0 命中 (姊妹表里没有 A 侧配对、A 表里没有 N 侧配对、平铺行里没有差集对、姊妹表里没有合并行) + 等式差 5 条(两条路径的长度/制表符/行数、三列行数与宽度展开的额外码数、携带差集对的行数与合并行数)。1⇒并到二十个国家码的那一行的行数(全表恰 1 行, 即最长合并行)；2⇒网页里 “1970” 的命中数; “public domain” 同值, 授权声明只住在散文里；5⇒两侧差集之差(只在 A 的配对数 − 只在 N 的配对数): 两边都非空才谈得上“不是重排”；6⇒归档后缀 “.tar.gz” 在网页的命中数(表侧为 0, 在 0 键里)；7⇒“@” 在网页的命中数(联系入口只在散文侧)；13⇒“tzdata” 在网页的命中数(表里从不写归档名)；26⇒网页里的制表符数 ⇎ 两份表的 825: 判格式靠分隔符密度而不是扩展名；34⇒A 侧第一个字段用逗号并了多国码的合并行数(它等于携带差集对的行数, 差值在 0 键里)；48⇒“数字点数字”的版本号写法在网页的命中数(表侧 0)；106⇒只在姊妹表 N 成立的(国家码, zone) 配对数: 它的正则分支在 A 里 0 命中；111⇒只在 A 成立的配对数; 机检侧等于各宽度桶展开出的额外码数之和；124⇒“两位大写逗号”形式在网页的命中数(散文里的行首码, 不是表行)；201⇒A 侧带第四列(注释)的行数 ⇎ N 侧 202: 差 1 行, 两侧结构同形；202⇒姊妹表 N 侧四列行数；278⇒A 侧一行一码的平铺行数(312 − 34): 这一批与姊妹表逐对一致, 是“分歧只在合并行”的下半句；312⇒A 侧数据行数(审计口径)；357⇒“href” 在网页的命中数(表侧 0)；418⇒姊妹表 N 数据行数(审计口径) ⇎ 312；825⇒A 侧制表符数 ⇎ F 侧同值(等式在 0 键里)；1038⇒姊妹表 N 侧制表符数；2087⇒网页左尖括号数(表侧 0)；2406⇒网页斜杠数(路径与标签的密度)；14482⇒A 内容区字符数(RCOT) ⇎ F 同值；65201⇒网页内容区字符数(RCOT): 比两份表都长, 却不是一行一事实。其中 5 条是差值/等式型而非直接计数型：两条路径的 RCOT 差、制表符差、行数差各一条，“三列行数 == 宽度展开的额外码数”一条，“携带差集对的行数 == 合并行数”一条——用差值表达是为了把“同一份的两个副本”这类断言留在机检范围内，而不是退回到不可复算的形容词。

※ 可核性的三级阶梯(本条最想把话说清楚的一处)：① 纯 CNT 可核：长度、行数、分隔符与标记字符的命中数、四类 0 命中，全部在 25 键里；② 需要外部断言：两份文件逐字节相同——本机用 hashlib/certutil 求摘要，算法名与 64 个十六进制字符都写在 src 行，不写成机检键，因为工具会把 “sha256” 里的 “256” 当成一个需要在源里逐字命中的硬数字；③ 只属于工具侧：字节数(归档成员 17592 ⇎ 网页 65372)与归档成员身份这类抓取元信息。再补一句诚实话：差集大小 111/106 是 Python 集合运算给出的，CNT 侧的对应证据是宽度桶之和与两个 0 命中分支式，两者同值不等于同一条计算——前者定义“差集”，后者证明“这些对在对方表里确实一次都不出现”。

※ 正则的逐行语义如何变成结论：re.findall 对长分支交替式给的是**不重叠命中**，也就是“含差集对的行数”而不是“差集对数”。第一次跑出 34 而不是 111 时看起来像 bug，顺着它去问“那 34 行是什么”，得到的却是本条最硬的一条：34 恰是合并行数，而“平铺行配差集对”的行式(另一条交替式)在 A 里 0 命中——于是分歧被定位到了写法层面：一行一码的那 278 行与姊妹表逐对一致，全部 111 对差异都住在用逗号并码的 34 行里。同一个 34 还是 “312 − 278” 的那个减数，所以这条结论有三个方向的支撑(行数、0 命中、行数差)。

※ 口径与“表里 0 次”的两重成因：审计证据范围会剔掉以 # 起始的行与出处头样式，于是同一批字节有两种行数：A 全文件 376 行(其中 63 行以 # 起始，另有一行空行) ⇎ 口径内 312 行数据；姊妹表全文件 449 行 ⇎ 口径内 418 行；网页全文件 1271 行且 0 行注释，全部落在口径内。字符数同理：A 内容区 14482 ⇎ 全文件 17536 字符(⇎ 磁盘 17592 字节，字节数只写在 src 行)。因此“1970”“public domain”这两个 0 有两重成因——它既不在数据行里，也不在算证据的那几行里，而是住在被剔掉的注释行；这也正是 0 键里那个零需要单独说明的原因：0 不是“没写”，是“写了但不在口径内”。

※ 四源对齐：A=zone1970.tab(口径内 14482 字符 ⇎ 磁盘 17592 字节) ≡ F=zone1970_latest.tab(口径内 14482 字符 ⇎ 17592 字节)；N=zone.tab(口径内 17501 字符)；H=zone1970.tab(口径内 65201 字符)。A 与 F 内容逐字节相同，所以二者的锚天然互相命中(摘要段 union_hit=50 与锚位数相等，同一串重复引用的锚位 37 个，不同串 13 个)——本条靠 ⟦LBL⟧ 标注区分两种到达路径，而不指望工具检查标签归位：atomcheck 与 audit 都是把同一 tag 的四个源拼在一起比对字面，标签写错不会 FAIL，这是作者的职责而不是机检的功劳。真正被机检的是对象类型：制表符 825 ⇎ 825 ⇎ 1038 ⇎ 26，尖括号 0 ⇎ 0 ⇎ 0 ⇎ 2087。

※ 隐性知识的所在(判词逐行对应的判断)：① 文件名是意图，内容是证据；② 同名不同物的两份文件会互相顶掉证据(这个目录里 zone1970.tab 是网页，zone1970_latest.tab 才是表)；③ “同一份”要哈希断言，长度/行数/分隔符只是下限；④ 姊妹表先算双侧差集再谈重排；⑤ 单侧空是包含，双侧空才是相同；⑥ 合并写法的展开增量恰等于一侧的独有配对数；⑦ 表回答归属不回答理由，理由住在注释与散文；⑧ 注释行会被口径剔掉，于是“表里 0 次”与“表里写着”同时为真；⑨ 报行数与字符数必须报口径；⑩ 缺席双向 ⇒ 三种对象互不包含，三份都得存；⑪ 版本号、授权这类元信息住在会被剥掉的那一层。与上一条的分工：那条数的是同一内容的两种序列化(层间差)，本条数的是同一个名字的三种对象(互不包含)，两条判据不重叠。

※ 实况：编码 5950 字符 ⇎ 摘要段 1857 字符(保留率 320.4%)，vs raw 源 4.985%，唯一码点 489，区块 8 类，字符/语义单元 5.99。拉丁字母：锚内 1405 ⇎ 锚外 155(其中出处标签 50)。全库现 45 条 / 已机检推导 423 条 / 全库保留率 **81.3%**。B45 的小整数待核为 0 项(整条没有需要挂起的数字切片)。

※ 保留率口径：本条 320.4% 高于 100% 是对照条的结构性结果——摘要段只索引锚点触到的窗口(四个源合计 111670 字符，窗口只取了 1857)，而判词要在四个源之间来回数(两侧差集、两条路径、双向缺席)，字符自然重于窗口。读它要按“25 键支撑 9 行判词”与 vs raw 源 4.985% 来读，不是按“少说了多少话”；若把网页那份当表来摘要，就会把对象差读成内容差，那正是本条要防的错。
