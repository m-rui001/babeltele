### ⟦A⟧ ⟸ corpus/raw/dhcp/rfc2131.txt

For example, in a 10Mb/sec Ethernet internetwork, the delay before the first retransmission SHOULD be 4 seconds randomized by the value of a uniform random number chosen from the range -1 to +1.

The retransmission delay SHOULD be doubled with subsequent retransmissions up to a maximum of 64 seconds. The client MAY provide an indication of retransmission attempts to the user as an indication of the progress of the configuration process.

T1 defaults to (0.5 * duration_of_lease). T2 defaults to (0.875 * duration_of_lease). Times T1 and T2 SHOULD be chosen with some random "fuzz" around a fixed value, to avoid synchronization of client reacquisition.

SOL_MAX_RT Option A DHCP server sends the SOL_MAX_RT option to a client to override the default value of SOL_MAX_RT.

A DHCP client MUST ignore any SOL_MAX_RT option values that are less than 60 or more than 86400.

The purpose of this mechanism is to give network administrators a way to avoid excessive DHCP traffic if all DHCP servers become unavailable. Therefore, this value is expected to be retained for as long as practically possible. An updated SOL_MAX_RT value applies only to the network interface on which the client received the SOL_MAX_RT option.

### 读法

一、四个答数写在四种载体里, 倍差却最大: 3600000 毫秒是 64000 毫秒的 56 倍余 16000。97 把它埋在散文里——同一段先给首枚延时 4 秒, 再要求“每次翻倍”, 于是 64 秒不是孤立字面而是序列末项(4→8→16→32→64 共 5 项, 末÷首=16=2^4); 03 把它钉成参数表里的一行(“120 secs”全文 2 处, 恰是 SOL ⇎ INF 两行, 客户端无从改变); 13 不进表, 它把 03 那两行用 OLD:/NEW: 原样重印再改(比值 30); 18 收下 3600 秒却来自表(28 行)。问“封顶在哪一秒”, 97 答的是自己翻倍的上限, 03/13/18 答的是 SOL_MAX_RT——同名不同量, 得先问管哪一步。
二、提案只改两枚, 标准落地四枚: 18 与 03 都有值的同名参数 21 枚, 同值 17 ⇎ 改动 ['SOL_MAX_RT', 120, 3600]⇎['INF_MAX_RT', 120, 3600]⇎['REL_MAX_RC', 5, 4]⇎['DEC_MAX_RC', 5, 4](闭合 0), 其中 SOL_MAX_RT ⇎ INF_MAX_RT 由 120→3600(比值 30), 另两枚 REL_MAX_RC ⇎ DEC_MAX_RC 由 5→4 是 18 自己改的、13 通篇没提(自改 2 枚)。13 的 9 枚标签行成对解出 4 对: 前缀/后缀两对只是散文替换, 无秒数; 行距合计 22。提案的 30 倍与标准的表间 30 倍是同一枚数(闭合 0)——这是全条最硬的一根桥: 一年前的“建议”与五年后的“缺省”在同一格对上。
三、可下发不等于照收: 18 在收下 13 的选项时写下夹逼 60..86400(比 1440 倍, 上下界与 13 各自闭合 0⇎0), 并规定越界即弃 ⟦D⟧⟨A DHCP client MUST ignore any SOL_MAX_RT option values that are less⟩(现读 SOL 1 ⇎ INF 1 处, 同份 MUST ignore any 共 11 处, 而 13 只 2 处)。它还独有两条例外: 值要留住 ⟦D⟧⟨this value is expected to be retained⟩(1 处) ⇎ 只在触发它的那块接口生效(2 处)——提案只改数值, 标准还得回答“这条覆盖算谁的、算多久”。两句在 13 都缺(0⇎0 处)。复写也不是逐字: 含夹逼式的行两份各 2 行, 配对 2 行里字节全等 0 ⇎ 仅标点差 0 ⇎ 归一也不同 2, 净增 20 字符——改的是措辞与角标。
四、次轴“多久去续租”换了基准: 97 写 T1=0.5×duration_of_lease ⇎ T2=0.875×同一标识符(全篇 2 处), 其 T2 式被排版劈在两行(原面 0 处 ⇎ 折平 1 处)——不折平的复算者会读成 0 处并断言“97 没写 T2 缺省式”。v6 三份改用 shortest preferred lifetime 作基准(1⇎0⇎2 处)并把 T1/T2 交给服务器下发; “infinity”一族的两种写法 1⇎4⇎0⇎11 ⇎ 10⇎7⇎0⇎13 处, 97 把它用在无限租约那一行。97 窗外的时长 60000 毫秒属于 v4 别的定时器, 把整篇值域当答案会读出另一个问题: 全库 1000..86400000 毫秒, 比 86400 倍余 0。
五、壳在这里比内容更能骗人: 四份全靠换页符分页(45⇎101⇎7⇎154 页), 页脚=换页符=行尾空格=“[Page ”子串四式逐份全等(合计闭合 0⇎0); 非空行有两个口径——按 isspace 判空 1800⇎3768⇎254⇎5875, 只认空格/制表/回车 1845⇎3869⇎261⇎6029, 差 45⇎101⇎7⇎154 恰是换页符独占行 45⇎101⇎7⇎154(闭合 0)。自编号另有两条隐形通道: 18 面内 “8415” 155 处, 其中每页重印的带空格页眉就占 153 行; 03 面内 “3315” 100 处 ⇎ 带空格式 100 ⇎ 黏写式 0(两式相加与引用总数逐份闭合 0)。义务词也不成差轴: 三词合计 231⇎215⇎22⇎359, 而 18 的答数行只是表里一个数——窗内三词合计 28⇎0⇎0⇎0(97 的答数句挂 SHOULD 写在散文里, 13⇎18 的窗只吞下表行)。
