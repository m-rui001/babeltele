### ⟦5077⟧ ⟸ corpus/raw/tlsTicket/rfc5077.txt

Zhou Obsoletes: 4507 Cisco Systems Category: Standards Track P.

This document applies to both TLS 1.0 defined in [RFC2246], and TLS 1.1 defined in [RFC4346].

The value indicates the lifetime in seconds as a 32-bit unsigned integer in network byte order relative to when the ticket is received. A value of zero is reserved to indicate that the lifetime of the ticket is unspecified.

The ticket lifetime may be longer than the 24-hour lifetime recommended in [RFC4346].

Rescorla Request for Comments: 8446 Mozilla Obsoletes: 5077, 5246, 6961 August 2018 Updates: 5705, 6066 Category: Standards Track ISSN: 2070-1721 The Transport Layer Security (TLS) Protocol Version 1.3 Abstract This document specifies version 1.3 of the Transport Layer Security (TLS) protocol.

Because ticket lifetimes are restricted to a week, 32 bits is enough to represent any plausible age, even in milliseconds.

Servers MUST NOT use any value greater than 604800 seconds (7 days). The value of zero indicates that the ticket should be discarded immediately. Clients MUST NOT cache tickets for longer than 7 days, regardless of the ticket_lifetime, and MAY delete tickets earlier based on local policy. A server MAY treat a ticket as valid for a shorter period of time than what is stated in the ticket_lifetime.

Client Tracking Prevention Clients SHOULD NOT reuse a ticket for multiple connections. Reuse of a ticket allows passive observers to correlate different connections.

### ⟦9001⟧ ⟸ corpus/raw/tlsTicket/rfc9001.txt

Clients can choose not to enable resumption to avoid creating this correlation. Clients SHOULD NOT reuse tickets as that allows entities other than the server to correlate connections; see Appendix C.4 of [TLS13].

[TLS13] sets a limit of seven days on the time between the original connection and any attempt to use 0-RTT.

### 本注的判断
四份文书答的不是同一个问题的四个答案, 而是把“票据能活多久 ⇎ 零值是什么意思 ⇎ 从哪一刻起算 ⇎ 一张票能不能复用”四件事拆给了四份: 4507 给字段与一个 hint, 零值只写成“寿命未定”(面内 1 枚), 并主动允许服务器把票当作“更短或更长”有效(1 枚)——它连一个上限数字都不给, 只引 2246 的 24 小时建议; 5077 把那段整句照搬(共尾共头各 62 枚词, 词集账闭合 0)⇎ 唯一补上的是计时起点 relative to when the ticket is received(2 枚), 仍不设上限; 8446 一次改五处: 字段改名去掉 hint(2 份面上 hint 式归零)、零值翻成“立即丢弃”(全库唯一, 判定 0⇒成立)、写出 MUST NOT 超 604800 秒即 7 日(每日 86400 秒⇒商 7 ⇎ 余 0)、把“或更长”砍掉只剩更短(段内 0 枚)、并把起点改写成 from the time of ticket issuance(1 枚, 唯一); 9001 一枚自己的时长规则都不写, 转述“[TLS13] sets a limit of seven days”(31 枚引用), 只另补一条复用禁令(4507/5077 面上 0 枚 ⇎ 8446 的“不该复用多连接”1 枚 ⇎ 9001 的“会让他人关联连接”1 枚——三份措辞互不相同)。
于是任何“取最新/取最全”的合并都会丢东西: 按年份最新取 9001(2021), 就丢掉 8446 面上那枚把上限钉死为整日数的算术(604800 = 86400 × 7, 余 0)与字段改名本身——9001 只说“[TLS13] 定了七天”, 自己既不给秒数也不定义零值(判定 1); 按“最严”取 8446, 就丢掉 5077 补的那句计时起点(8446 把它换成“自签发起”, 两份的起点并不等价)与 4507/5077 的“可更长”自由度; 按“最原始”取 4507, 就同时丢掉上限、丢弃语义与复用禁令。逐字搬运在这条里是真的行级搬运: 4507·5077 那对共用 259 枚长行, 其中 235 枚逐字节同形 ⇎ 24 枚只差缩进, 轴账 case2⇎hyph0⇎space28⇎multi0 闭合 0——但搬运只发生在 4507→5077 一步, 8446 起就是重写(与 5077 段的共头只 1 枚词)。
### 不可由在库文件判定(只写在这里, 不进判词与门槛)
四份 .txt 的抓取时刻与磁盘 mtime 谁新谁旧; rfc-editor.org 此刻给这四份挂的现行状态页与勘误页(含 4507/5077 此后被改判为 Experimental 一事——本注只能读面上自带的类目行 Standards Track 1 ⇎ 1 ⇎ 1 ⇎ 1 ⇎ Experimental 0 ⇎ 0 ⇎ 0 ⇎ 0 枚, 读不出站点的当前标注); 这条链条之外被引用的 RFC 2246/4346 不在库内(库内 rfc*.txt 共 43 份, 2246 0 ⇎ 4346 0, 而四份面上对 2246 的引用共 8 枚——那句“24 小时建议”的原句读不到); 5246 在库内(1)但不属于这条的四份源; 9001 转述的 [TLS13] 就是库内的 8446, 但这条等式来自文档惯例而非在库字节自证; 此后哪份在途文书又动了票据寿命; 现网实现实际缓存多久、要不要复用一张票(“票据是一次用的 ⇎ 可重放的”是实现事实, 不是文书事实)。
以上量要么在本机之外、要么随实现与站点漂移, 复算通道里没有它们的位置; 门槛只认在库字节。
